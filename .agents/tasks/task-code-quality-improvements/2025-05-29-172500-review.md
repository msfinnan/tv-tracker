# Code quality extraction and component decomposition

A housekeeping refactor that consolidates duplicated constants (status labels, priority options, storage key, default platforms) into `src/constants.ts`, extracts utility functions (`generateId`, `formatProgress`, `downloadJson`) into `src/utils.ts`, pulls the ShowCard edit form into its own component, replaces unsafe type assertions with type guards in ShowList, and optimizes StatsDashboard to single-pass counting. The change also adds an empty-platforms guard in App.tsx and fixes a missing mock in ShowCard tests.

**Watch for:** The ShowCard priority select now renders full-length labels ("1 — Must watch") where it previously rendered compact "P1" labels — this is a behavioral/UI change, not just a refactor (confirmed). The `loadPlatforms()` double-call on mount was a stated objective to fix but remains unfixed in the diff (confirmed). The `useCallback` on PlatformTabs' `handleAdd` wraps a `prompt()` call, providing no real memoization benefit (confirmed).

## High-level view

The ShowCardEditForm extraction reduces ShowCard from ~140 to ~80 lines. `ShowCardEditForm` initializes state from props on mount but won't track prop changes — fine while editing locks the card, but a gap if the app gains real-time sync.

The `loadPlatforms()` call in App.tsx is duplicated: once as the `useState` lazy initializer for `platforms`, and again inside the `activeId` initializer. The stated fix (using a single `initialPlatforms` variable) was described in the task file but never implemented in the actual code.

The ShowCard priority select previously used compact labels ("P1"–"P5") suited for a constrained card layout. After this change, it renders the same verbose labels ("1 — Must watch") used in the AddShowForm modal. If the card's CSS expects short text, this could overflow or wrap.

## Priority labels: compact vs. verbose

The original ShowCard rendered priority as "P1" through "P5" — short enough for a compact control row. The AddShowForm rendered full labels "1 — Must watch" etc. in a modal where space is generous. By sharing `PRIORITY_OPTIONS` across both, the refactor unifies the labels but introduces a UI regression in the card context: a dropdown that was ~20px wide now needs ~120px.

The fix is straightforward: either give `PRIORITY_OPTIONS` both a `label` and a `shortLabel` field, or define a separate `PRIORITY_SHORT_LABELS` for the card select. The current implementation in ShowCard:

```tsx
{PRIORITY_OPTIONS.map(opt => (
  <option key={opt.value} value={opt.value}>{opt.label}</option>
))}
```

should render a short form when used inside the compact card layout.

## Double localStorage parse on mount

Line 12 of App.tsx:

```tsx
const [platforms, setPlatforms] = useState<Platform[]>(loadPlatforms)
const [activeId, setActiveId] = useState<string>(() => loadPlatforms()[0]?.id ?? '')
```

Both calls hit `localStorage.getItem` and `JSON.parse`. The task description in FEAT-001.json explicitly calls out this bug and proposes `const initialPlatforms = loadPlatforms()` used for both, but the shipped code doesn't implement that pattern. This is a missed objective — not a regression (it existed before), but it was supposed to be fixed by this PR.

## useCallback without memo boundary

PlatformTabs wraps `handleAdd` in `useCallback` with `[onAddPlatform]` as the dependency. For `useCallback` to prevent re-renders, the child receiving the callback must be memoized (via `React.memo` or `useMemo`). Here, the `<button>` receiving `handleAdd` is a plain JSX element inside the same component — it always re-renders when PlatformTabs re-renders. The `useCallback` adds indirection without benefit.

## Missing test coverage for new modules

`src/utils.ts` contains three functions. `formatProgress` has non-obvious edge cases (season=0 is falsy, episode=0 is falsy, both undefined returns null). `downloadJson` manipulates the DOM (creates/clicks/removes an anchor). None of these have dedicated tests. The existing ShowCard tests exercise `formatProgress` indirectly through rendering, but there's no unit-level coverage for the utility module.
