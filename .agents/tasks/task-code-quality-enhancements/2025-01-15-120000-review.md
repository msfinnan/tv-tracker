# Module extraction and storage hardening for TV Tracker

This change decomposes several monolithic component files into focused modules: shared types (`ShowPatch`, `Priority`) into `types.ts`, utility functions (`uid`, `formatProgress`) into `utils.ts`, UI constants (`STATUS_LABELS`, `STATUS_CYCLE`, `PRIORITY_OPTIONS`) into `constants.ts`, and validation logic (`isValidShow`, `isValidPlatform`, `validateImportData`) into `validation.ts`. Alongside the extraction, `loadPlatforms()` gains runtime validation of localStorage data, a double-call bug in `App.tsx` initialization is fixed, and test helpers are brought up to date with the current prop contracts. A new `SearchBar.test.tsx` rounds out component test coverage.

**Watch for:** The `isValidShow` validator checks `typeof priority === 'number'` but doesn't verify the value falls within 1-5, meaning corrupt priority values (e.g. 0, 99) pass validation and produce a `Priority` type assertion that the compiler trusts but the runtime doesn't enforce (confirmed). The `PRIORITY_OPTIONS` constant is exported but never consumed by `AddShowForm`, which still hard-codes its `<option>` elements (confirmed, minor inconsistency).

## High-level view

The `Priority` union type tightens the contract at compile time, but runtime enforcement at both the DOM boundary (`as Priority` casts) and the storage boundary (`isValidShow`) is incomplete—invalid numeric values pass through unchecked.

The double-`loadPlatforms()` fix in `App.tsx` eliminates a redundant localStorage parse that could diverge from the `platforms` state. The new code references the already-loaded `platforms` array via the synchronous ordering of `useState` initializers.

Storage hardening via `isValidPlatform` in `loadPlatforms()` protects against corrupted localStorage, but the validator accepts any numeric priority (not just 1-5), so out-of-range values propagate as trusted `Priority` values.

## Priority type: compile-time union vs. runtime validation gap

At the DOM boundary, `Number(e.target.value) as Priority` is the standard escape hatch when a controlled `<select>` guarantees valid options—acceptable here because the options are static.

The deeper issue is in `isValidShow`:

```ts
typeof obj.priority === 'number'
```

This is the runtime gate that decides whether localStorage data is trusted as `Show`. It doesn't check `obj.priority >= 1 && obj.priority <= 5`, so a show with `priority: 0` or `priority: 99` passes validation and flows into the app typed as `Priority`. The type guard's return type `s is Show` means downstream code trusts `show.priority` to be `1 | 2 | 3 | 4 | 5`, but it might not be. The select dropdown would render with no option selected or an unexpected value attribute.

## Double-load fix and the useState initializer closure

The original code:

```ts
const [platforms, setPlatforms] = useState<Platform[]>(loadPlatforms)
const [activeId, setActiveId] = useState<string>(() => loadPlatforms()[0]?.id ?? '')
```

Called `loadPlatforms()` twice—once for the state value, once for the initial `activeId`. The fix references `platforms` directly in the second initializer. This works because React calls `useState` initializers synchronously in order during the first render, so `platforms` is already populated when the `activeId` initializer runs.

## PRIORITY_OPTIONS drift risk

`constants.ts` exports `PRIORITY_OPTIONS` as a structured array of `{ value, label }` pairs, but `AddShowForm.tsx` still renders its options inline:

```tsx
<option value={1}>1 — Must watch</option>
<option value={2}>2 — High</option>
...
```

If the labels or range ever change, the constant and the component would need separate updates.
